# Joined vertexmesh CPU render path

2026-10-10. Module `vertmesh_render.rs`, CLI `rc-vertmesh-render-check`.
Five completed integration tasks:

1. Use the RenderPreProcess vertex/UV stream as the actual GetFrame destination.
2. Derive actor absolute scale and projected W through GetAbsMax and Project.
3. Select camera LOD and evaluate both native draw gates in their original order.
4. Execute the existing instance/channel/cache/frame path at the +dc handoff,
   deriving the count-pointer writeback instead of accepting a supplied answer.
5. Commit the generated stream, section headers, instance and render state together,
   including rollback after late geometry/upload/material errors.

## Data flow

`Request` combines preprocessing, supplied scene matrix and actor position/scale,
camera parameters, actor/owner/fallback states, +dc argument addresses, the existing
vertexmesh instance input and geometry/material/upload snapshots.

`Runtime.submit_vertmesh_render` first prepares sections/UVs, evaluates GetAbsMax
and Project, and replaces the camera's supplied `actor_abs_max` and `projected_w`.
It synchronizes section count/header input from the prepared state. If preprocessing
ran, face records and low16 wedge mappings also come from that preprocessing input.
If it was skipped, unused preprocessing source arrays are not consulted.

LOD arithmetic runs before the no-sections and no-actor-state gates, as in the
original `105602bb..105602fa` sequence. A disabled draw still commits preprocessing
and derived camera snapshots, but does not validate/access instance channels,
frame banks, callback addresses or upload/material inputs. Runtime remains unchanged.

For an enabled draw, camera vertex count must match the instance and its mesh identity
must match the geometry material mesh address. Signed stream count is 0..65536,
stream size is exactly count *32, and the geometry wedge array has the same count.
Receiver/source/count-pointer addresses must be nonzero and bounded against wrap.
The original +dc arguments are actor, scene, prepared stream, stride32, countpointer,
mode0. The plan records the exact call and before/after counts.

The joined path derives frame requested count from selected LOD, forces mode0 and
stride32, and replaces stale frame wedge/byte inputs with the canonical mesh mapping
and prepared stream. The instance adapter derives sequence, time and cache as before.
Its output supplies actual count writeback and generated upload bytes. Geometry keeps
the pre-callback LOD; in this joined camera path the original signed upper clamp
already ensures an ordinary valid LOD does not exceed mesh vertex count.

On success the request stores generated bytes in both instance output and the canonical
preprocessing stream. Canonical preprocessing section bytes come from the post-index
mesh headers. `Plan.preprocessing` remains the snapshot before frame/index mutations;
the geometry input remains the pre-index snapshot and its nested mesh contains the
post-index header image, following the existing geometry adapter convention.
The redundant legacy camera/frame/callback answers are synchronized on success.

Preprocessing, derived camera, channel refresh, cache reset/animation, geometry,
uploads, materials and runtime are one transaction for error handling. All fallible
work before the nested draw touches a local request. The nested instance/geometry
operation is already atomic, and only infallible snapshot commits follow its success.

## Original replay

The recorder composes the existing independently checked native preprocessing,
Core GetAbsMax, Engine Project, camera LOD/gates and instance bodies with the
geometry/upload/material replay. Logical array allocators, virtual name lookup,
material and COM answers remain explicit boundaries. The temporary MXCSR floor
used inside frame scheduling still restores default rounding before later LOD calls.

The original GetFrame body now uses the caller's actual prepared stream address
`72000000`, countpointer `27ffffcc` and shared mesh address `39000000`. Original
count-pointer stores and output bytes are checked at those addresses. The selected
opaque sequence pointer remains the scheduler's record address. The downstream
vertex-source payload is replaced by these generated bytes, not a separate fixture
answer. Supplied matrices and stored FPTAN result are still inputs; the transform
setup preceding the camera region is not executed by this joined proof.

**50 sequences / 146 render requests**, **593,431 original instructions**:

- 112 enabled draws, 14 no-sections and 20 no-actor-state early returns.
- 146 Project and 146 GetAbsMax calls.
- 101 preprocessing runs /45 skips, 505 UV copies, 261 section constructors.
- 112 actual GetFrame stream/count-pointer handoffs, 75 cache initializations /
  37 reuses, 28 editor lookups, 139 direct /136 interpolated vertices.
- 1,353 generated indices, 112 vertex and 112 index uploads,
  **253 draws /506 material passes**; 83 zero-primitive sections skipped.

Component instruction counters overlap this total and must not be added to it.
Complete plans, requests and runtime snapshots match the native replay. Synthetic
input deliberately supplies stale NaN camera answers, invalid legacy frame layout/
count/mapping/byte answers, invalid unused channels behind disabled gates, and stale
callback count_after. Their authoritative replacements and skipped reads are checked.

**12 full rollback cases** cover preprocessing counts/allocation, nonfinite actor/
matrix values, tangent denominator, callback receiver, missing channels, conflicting
vertex count/stream count, and late unlock/material/index errors. Request and runtime
remain byte-for-byte unchanged, including pending preprocessing and editor/cache work.

**920 existing workspace tests passed**, plus the new native integration cases;
no new unit-test count is claimed. Debug/Release reports are byte identical;
Clippy all targets with `-D warnings`, formatting and diff checks passed.

This is a joined CPU model with synthetic animation banks and supplied responses,
not original clip playback or a playable game. Still open: MeshToWorld and renderer
transform setup, camera matrix construction, FPTAN, asset/name loading, native
allocator ownership/capacity behavior, actual material compilation and GPU execution.
